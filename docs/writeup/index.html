Learn mode

Claude does the work. You learn from it while it happens.

Arvind ant-takehome.vercel.app github.com/arvindm1991/ant-takehome

The problem

“When AI agents handle complex tasks autonomously, humans can become passive observers rather than active learners, missing opportunities to develop their own skills and understanding.”The brief, challenge 2: Cognitive engagement

That's the problem I took on. Agents are a forklift in the gym and a microwave in the kitchen: the work gets done, but the muscle doesn't grow, the knives go dull and the pots rust. Showing more of the work doesn't fix it. Claude already shows its reasoning and code, and people skip to the answer.

The good news: unlike a course, this isn't learning for its own sake. The task is real, the person just asked for it, and an expert is doing it right now. It's on-the-job training, where you learn the job while a skilled hand does it.

The goal: add back the right amount of effort for the learner while the work gets done, without slowing the work down.

Why Option B

Option A is customer education: teaching people Claude's features. Option B is general education: helping people get better at their own work, whether that's programming, writing or analysis. B is the bigger opportunity. Finding features matters, but people losing their own skills is the bigger risk, and it grows as agents take on more of the work.

It was also a personal choice. I trained as an aerospace engineer, then built an award-winning edtech company and have stayed in education since. I care about building learning that is pedagogically sound and realistic for the next generation of learners, and I was already working on ideas in this space. Option B was an easy pick.

Why inside Claude, not a separate app

When something needs doing, people go where it gets done fastest. That's why so many good learning products get little use; I've built some of them. A separate learning app that makes you work for the answer is counter 1: good for the few who choose it, empty for everyone else.

So I didn't build counter 1. Learn mode puts the teaching at counter 2, inside the Claude session where people already are, and it never makes the task wait.

What I built

Learn mode is a switch in Claude. When it's on, a learning agent runs alongside Claude. Claude does the task exactly as it would anyway; the learning agent watches Claude's work and teaches you from it.

Claude (main agent)Does the task at full quality. Doesn't know Learn mode exists; nothing about the learner enters its context.
→read-only
Learn mode (learning agent)Reads Claude's plan, files and code as they appear, and teaches from them.

One journey: “Build a login page with JWT auth for this app”

  1. Turn on Learn mode (or tap the suggestion under a task). Claude starts working; you're never in its way.
  2. Pick what to learn. Goals come from the task itself: where login plugs into this repo, what a server must check before it trusts a login token, why passwords are hashed with bcrypt.
  3. See it first. An interactive built from Claude's code, like a visualizer that decodes the token Claude's login will issue.
  4. Predict before Claude writes it. “What must verifyToken() check?” When the file appears, Learn mode checks your answer against the real code and links to the line.
  5. Go where you want. Go deeper, step sideways or try it hands-on. After a miss: a hint, an interactive, or the exact spot in Claude's code.
  6. It comes back. A recap shows what moved. Days later, or when a related task comes up, a one-question refresher brings the topic back.

How the learning agent works

It's a real agent, kept on a short leash. It chooses its own actions with tools, remembers the learner across sessions, and works toward the goal the learner picked. It doesn't run unattended: it acts when something happens, one decision at a time.

What it sees each turn

  • What you asked Claude, and Claude's steps so far: plan, files read, code written. Steps Claude hasn't shown yet appear by name only, so it can ask you to predict them without giving them away.
  • What it knows about you: how well you know each topic, mistakes you keep making, your last few answers.
  • Your goal and the conversation so far.
  • A one-line teaching approach chosen by code from your level. For example: new to this, so show it first; missed twice, so show it and then ask something easier.

What it can do

ToolWhat it's for
Suggest goals4–5 things worth learning from this task, from where to look in the repo to a stretch goal.
Ask a questionPredict the next step, explain it back, “what if…”, or pick the files you'd open. It writes the answer key from Claude's code.
Build an interactiveIts preferred way to teach. A separate Opus call builds it from Claude's code and runs it in a sandbox with no network access.
Hint · Explain · Wrap upA nudge that never gives the answer; a short explanation tied to Claude's code; a recap when the goal is done.

Everything it produces has to point at the step in Claude's work it's about; references to steps that don't exist are dropped. Two helpers sit beside it: a grader (Sonnet) that scores written answers against the answer key and names the misconception, and a quick check (Haiku) that decides whether a task is worth learning from at all.

When it acts

It responds to events: a task starts, you pick a goal, you answer, you pick a next step or type a question, or Claude writes a step you made a prediction about. It keeps going on its own where that helps. After you pick the files you'd open, it moves to the next question while Claude is still reading, then checks your picks against the files Claude actually opened. Once you've answered three questions on a goal, it wraps up with a recap.

Getting ahead of Claude

Claude never waits for Learn mode and isn't influenced by it. Learn mode gets ahead by reading Claude's reasoning as it streams and the plan Claude makes before it writes code. That's how it can ask you to predict verifyToken() before the file exists. In a real integration it could start even earlier, as soon as the main agent's own reasoning is available.

Why keep it on a short leash

One decision per event, a few questions per goal, and rate limits per person and per day keep cost and attention in check. The main agent is protected too: learner data never enters Claude's context, and a test fails if the main agent's code ever imports the learning code.

How it remembers what you know

  • The model grades, code keeps score. The grader says right, partly right or wrong. Plain code turns that into a score, so scores are consistent and can be checked.
  • A score per topic starts at 30% and moves toward each new result. Predictions and “what if” answers move it more than recall. An answer given after a hint counts for less.
  • Every attempt is kept as evidence: the question, your answer, the result, and which step of Claude's work it was about. The agent sees your recent attempts, and the recap shows before and after.
  • Misconceptions stay open (for example, “the token's contents are encrypted”) until you later get that topic right without a hint. The agent aims questions at them.
  • Spaced review. A topic comes back after 1, 3, 7, 16 and 35 days. A right answer pushes it further out; a miss brings it back tomorrow. Due topics under 70% show up as refreshers.
  • Related work brings topics back. When a new task touches something you learned, you get a one-question refresher there, or a question that connects the two (bcrypt and rate limiting, say).
  • Where it lives: in the browser for the prototype. The same shape would move to Claude's memory.

How I got here

  • The first idea everyone had was wrong. Every model I brainstormed with, Claude included, first suggested pausing the agent at key decisions and letting the user choose. That makes the work only as good as the learner, and fills the agent's context with guesses. So the learner rides alongside instead of steering.
  • Spec before code. A numbered log of decisions and six milestones, each tested before the next.
  • Real Claude API from the start. Opus for the main agent (reasoning streamed live), Sonnet for the learning agent and grader, Haiku for the “worth learning?” check, and Opus for interactives.
  • Changed it after using it. A blank chat box felt like “a second Claude”, so it became goals and next steps. That felt like homework, so now it shows before it asks, has one text box of its own, and starts by itself when Learn mode is on. Then I made it work on phones.
  • Safe for a public link. Rate limits, size limits, and prompts that treat Claude's output and user text as material, not instructions.

Keeping people in charge

  • Claude still does the task, fully. Learning never blocks it, slows it or changes it.
  • You choose whether to learn, what, and how deep. Everything can be skipped, and Learn mode is one switch.
  • Understand before you review. Knowing why Claude made each choice is what lets you check its work and push back.
  • It never does the task for you. It shows, asks and checks. It asks about Claude's choices rather than judging them, because it doesn't have Claude's full context.

Measuring success

  • Main measure: how often people get a refresher right on the first try, days later and in a different task. It shows what stuck, not how long anyone spent.
  • Progress: topic scores over time, and misconceptions cleared.
  • Adoption: offered → opened → first answer → goal finished, compared for the switch and the in-chat suggestion.
  • Guardrails: no change to how long tasks take or how happy people are with them; how often people switch it off; how often people type a request for Claude into Learn mode's box.
  • Checks on the learning agent: it uses Claude's actual code, doesn't give away answers, grades like a human would, and shows before it tells.

Scaling to millions

  • No new app to find: it's a switch in Claude and Claude Code.
  • Works beyond code: topics come from the work itself, not a hand-written course. The same loop fits writing and analysis.
  • Different defaults for different people: on by default for students (set by schools); off for professionals, with occasional suggestions; stretch goals and review for experienced users.
  • Cost follows use: it only runs when on; Sonnet and Haiku do the watching and deciding; Opus builds interactives only when someone asks to see or try something.
  • Rollout: behind a flag, then compare the switch against in-chat suggestions, and keep it if the main measure improves without hurting the guardrails.

Simulated in the prototype: the repository Claude works on, the pacing of Claude's steps, and a “+3 days” clock for trying spaced review. If API credits run out, the app falls back to a scripted version of the demo.
